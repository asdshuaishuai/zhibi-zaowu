# 执笔（ZhiBi）3.0 — 跨端超级重构 · UI/UX 与架构设计 v0.1

> **还是执笔**——这是一次彻底的超级大重构，不是新产品。口号升级：**人执笔，AI 研墨**——AI 负责磨墨备纸（搭骨架、理台账、查矛盾、给续写建议），笔永远在作者手里。

技术栈全换：macOS SwiftUI 单端实现 → **DeepSeek Harness（DSH）agent 底座 + GPUI Kit 跨端前端**（macOS / Windows / Linux）。执笔的全部能力 1:1 复刻进新底座，并以**彩云小梦式人机共写**补上「写的时候 AI 就在旁边」这一执笔缺的体验。老项目（zhibi/，SwiftUI）保留不动，数据目录双向兼容。

---

## 1. 产品定位与不变量

| 不变量 | 说明 |
|---|---|
| **人主 AI 辅** | 正文永远作者亲笔；AI 的一切产出（含整章草稿、续写片段）只能以**提案**形态存在，作者采纳前不落盘 |
| **就地反馈** | 凡是在某个窗口/按钮触发的 AI 行为，结果就在那个窗口里过目与采纳，不逼用户绕道收件箱 |
| **全程可视化** | AI 的每一步（准备上下文 → 工具调用 → 结果回灌 → 流式产出 → 完成/失败）在**右侧 Agent 轨迹 Dock** 像对话一样全程可见——这是本作的门户级特性，不是隐藏面板 |
| **跨端一致** | 一套 Rust 代码（GPUI）出 macOS / Windows / Linux；数据目录格式沿用执笔（人随时带走稿子） |

## 2. 技术架构

```
┌────────────────────────────────────────────────────────┐
│                执笔 GPUI 桌面应用（Rust）                 │
│  gpui-kit：Dock / 虚拟列表 / 编辑器 / Markdown 渲染        │
└──────────────┬─────────────────────────────────────────┘
               │ NDJSON JSON-RPC over stdio
               │  ├─ 请求：开 session / 发 prompt / 审批工具
               │  └─ 通知：session.event（全量事件流→轨迹面板）
┌──────────────▼─────────────────────────────────────────┐
│         DSH runtime（`dsh --profile sdk` 子进程）         │
│  Cordis 插件树：模型适配 / 工具注册 / 会话日志 / 审批策略     │
│  ┌─────────────────────────────────────────────────┐   │
│  │  novel-pack（我们的 Cordis 插件包，dsh.bundle）      │   │
│  │  · propose_* 提案工具（复刻执笔 30+ 工具面）          │   │
│  │  · 确定性工具（骨架闸门/连贯性扫描/AI味扫描/对账）      │   │
│  │  · PromptLibrary + 创作法典（13 流派 + 网文/传统两法）  │   │
│  │  · project-store 服务（.zhibi 兼容目录读写）          │   │
│  └─────────────────────────────────────────────────┘   │
└──────────────┬─────────────────────────────────────────┘
               │ OpenAI 兼容 SSE（DeepSeek / GLM / Kimi / Ollama / 局域网端点）
               ▼
                 LLM
```

要点：

- **GPUI 前端不实现 agent 循环**。每次 AI 任务 = 开/复用一个 DSH session，发 prompt，收 `session.event` 流。轨迹面板的数据源就是这条流 + 会话日志（append-only，天然可回放、跨启动保留）。
- **novel-pack 是普通 DSH 插件**（`dsh.bundle` manifest + cordis patch），不 fork DSH 内核；上游更新可跟。
- **提案落盘在宿主侧**：`propose_*` 工具由 novel-pack 落到 `proposals/inbox.json`，GPUI 侧通过工具结果事件 + 文件监视双通道感知。采纳 = 前端点按钮 → 调 novel-pack 的确定性 `apply_*` 工具（幂等保护沿用执笔：同题保护、同 id 合并、快照回滚）。
- **执笔的项目目录格式原样沿用**（`<书名>.zhibi/`：project.json + canon/ + outline.json + clues.json + memory.json + proposals/ + chapters/ch-NNN/）——老用户的项目文件直接打开。

## 4. 核心界面详设

### 4.1 写作台（编辑器）——本作的灵魂

稿纸居中（约 720px 栏宽），纸感底色，宋体正文可选。执笔的功能位原样保留：章节状态、字数进度环、快照/回滚、专注模式（⌘⇧F 全窗只剩稿纸）。

**彩云小梦式共写（提案制改造版）**——执笔的「生成后再看」升级为「写时陪伴」：

1. **续写幽灵（Ghost Continuation）**：光标停在段尾 ≥1.2s，自动请求续写 1-2 句，以灰斜体幽灵文本显示在光标后。`Tab` 逐句采纳（采纳的句子转为正文并续请求下一句），`Esc` 拒绝，继续打字即自动作废。幽灵文本**不是正文**，落盘只发生采纳那一刻——提案铁律的最小颗粒度。
2. **分支卡（Three Branches）**：段尾按 `⌘⇧→` 或点「给我几个走向」，AI 一次给 **3 个走向**（各 80-150 字）：走复仇线 / 走师门线 / 走温情线，每张卡片带情绪标签与伏笔影响提示。点选一张 → 该走向展开为完整段落草稿（仍以**草稿提案**形态挂在当前章下方），作者可再改再采纳。`换一批` 重新生成，`全部不要` 关闭。
3. **选区改写菜单**：选中一段 → 浮出菜单：**拉深**（小梦的招牌：同一段写得更细更满）/ **扩写** / **精简** / **换一种写法** / **去AI味改写**。产出以 diff 预览（原文 vs 建议）就地展示，逐条采纳，采纳前自动快照。
4. **分叉点标记**：被分支卡替换或从幽灵文本生长出的段落，左缘留一枚小墨点标记「此段有 AI 参与」，悬停可回看当时的轨迹跳转——共写透明化，正文主权可追溯。

共写请求与重型任务共用同一个轨迹面板（轻量请求标记为「续写」小节点，不淹没主轨迹）。

### 4.2 右侧 Agent 轨迹 Dock

沿用执笔 AgentTrajectoryPanel 的对话式设计并强化：

- 数据源：DSH `session.event` 流（工具调用/结果/文本增量/完成原因全部有事件），按「一次 prompt = 一个会话块」分节。
- 每个块：能力名 + 开始时间；内部气泡：🛠 工具调用（含参数摘要）、↳ 工具结果、💬 流式输出（运行中实时滚动）、✓ 完成（新登记 N 提案）/ ✕ 失败（原因）。
- 点击任何「已登记提案」气泡 → 跳到提案页高亮该提案；点击「写入正文」气泡 → 跳到对应章节位置。**轨迹是可导航的**。
- 顶部过滤：全部 / 仅工具 / 仅文本；运行中顶部有停止按钮。
- 轨迹持久化由 DSH 会话日志承担，重启后可回看。

### 4.3 提案收件箱（Dock 第二页 + 独立台账页）

- 提案卡按 payload 类型渲染（骨架/草稿/伏笔/设定/归类/档案卡/报告…），沿用执笔的视觉语言：标题 + 内容预览 + 采纳/拒绝。
- **就地反馈规则**继续生效：设定归类、整理旧稿、导入后归类等，在触发窗口内直接内嵌结果列表 + 全部采纳；收件箱是留痕与逐条细调的地方，不是唯一入口。
- 批量操作、拒收理由（回灌质量反馈回路）、采纳率统计页保留。

### 4.4 台账页（大纲/时间线、伏笔、设定、人物、记忆、统计）

全部按执笔的信息架构 1:1 复刻，视觉按 GPUI 组件体系重绘：

- **大纲·时间线**：故事线健康度 chips + 双栏时间线表（作者真相｜读者已知）+ 大纲对账条（计划 vs 实际）+ 「AI 建大纲/同步大纲」提案按钮。
- **伏笔台账**：表格（编号/标题/状态/节奏/埋点章/最近动作）+ 健康条 + 「AI 盘点」；埋点修复单条采纳。
- **设定**：左分组树（世界观/势力人物/修炼体系/剧情大纲/题材规则）+ 右 md 编辑；右键：改类别/复制/访达/删除（含确认与 md 同步清理）。
- **记忆中枢**：事实账本 + 矛盾体检 + 人物归一 + 长程档案卡（检索框 + 卡片流）。
- **统计**：每日目标进度环、14 天柱状图、连续天数、AI 采纳率。

### 4.5 书架（首页）

书卡网格（SVG 封面 + 书名 + 字数 + 最近编辑），新建向导（书名/题材 chips/一句话核心 → 自动「搭框架」提案流程），导入向导（oh-story 一等支持；**导入窗内跑完 AI 归类并就地反馈**，执笔已验证的交互直接带过来），选题调研入口。

### 4.6 设置

三分区沿用执笔：通用（目标/主题）、模型服务（预设目录 models.dev + 自定义 OpenAI 兼容端点 + **连通性测试**）、生成与上下文（包预算/自动保存）。DSH 的模型适配插件直接复用，我们的配置面板写 DSH 的 profile 配置。

### 第一轮（M1–M6）：能写、能提案、能打包

- **M1 骨架可跑**：GPUI 窗口 + Dock/侧栏布局 + DSH sdk 子进程连通。
- **M2 项目与编辑器**：.zhibi 读写 + 稿纸编辑器 + 章节树/书架。
- **M3 提案闭环**：novel-pack 首批工具 + 收件箱 + 就地采纳 + 状态条。
- **M4 彩云式共写**：幽灵续写 + 分支卡 + 选区改写。
- **M5 全能力复刻**：审查/对账/去AI味/记忆/图谱/导入导出/统计。
- **M6 跨端打包**：Win/Linux 适配 + 打包。

### 第二轮（M0–M9）：AI 体系与作者主权

- **M0 运行环境**：只用 DSH 的 sdk profile，剥离 web/桌面端；封闭包 274MB，
  升级只需改 `runtime/zhibi-runtime/package.json` 一处版本号。结论见 `SPIKE-M0.md`。
- **M1 Agent 体系**：每本书一个 DSH 进程（`DSH_HOME` + cwd 都指这本书）；
  懒启动 + 空闲回收 + **进程数上限**（默认 2，`settings.maxRuntimeProcs`）；
  托管 / 极简 / 创造三模式；6 个内置专属 Agent；审批与提问弹窗；
  停止 = 杀进程 + `session/resume`。`Workspace` / `Inner` 的 Drop 负责真正
  kill 子进程（`Child` 的 Drop 不杀进程，Node 会留在后台），句柄死掉时
  下次发送自动重建，不会对着已关闭的 stdin 报"运行时已退出"。
- **M2 设置中心**：账号余额、模型与推理强度、通用设置、模式说明、
  **保存即重启运行时**（否则作者以为关掉的联网已经生效，实际这一轮还能联网）、
  **内置插件开关**（按 patch 行粒度，只列可安全关的项，并在关掉时显示代价）、

- **M3 作者主权**：改动日志（JSONL + 内容寻址前像）、单条/整批撤销含冲突检测、
  AI 参与墨点、写作档位闸门（辅助/共写/代笔 + 逐章授权）、
  **台账结构校验 + 整档回滚**（`app/src/schema.rs`）：采纳前后像，校验不过
  整档退回并保持提案待审；AI 绕过工具直写的台账在回合结束时校验并按
  journal 回滚，作者之后手改过则报冲突不覆盖。
- **剧情画布 = 力导向关系图**（`graph_layout.rs`，纯函数带 12 项测试）：
  Fruchterman-Reingold 力导向（相连的互相拉近、所有节点互相排斥），
  主角钉在原点——作者要的是"围绕主角"，不能让力把它推到角落。
  几条实现约定：初始位置按 (类型, 名字) 的名次摆（台账顺序变化不改图形）、
  节点被关在 `sqrt(n)·k·1.2` 的框内（**没有这条就会发散**，实测能漂到 8 万像素）、
  最后再做几十轮去重叠（卡片有实际尺寸）。
  **连不上主角的节点进"孤儿区"**（主图下方虚线围栏）——它们不是丢弃，
  是"还没接上主线"，单独放一块才看得出该补关系还是本来就是背景。
  布局换代用 `canvas.json.layoutVersion` 作废旧坐标与旧视角，并自动"适应窗口"。
- **M4 人物实体**：`characters.json` + 无损迁移 + 可编辑档案页（字段锁、合并、别名）。
- **M5 关系网**：`relations.json`，一条关系多个章节区间（起止章 + 读者可见），

  侧板只给**简略章号**（`5–19 → 20–`），两条"更细"的出路是点名字跳人物卡、
  点章号就地展开每一段的标签与明暗，而不是把 226px 的侧板撑成第二份档案；
  关系维挂 `relations` Agent 的模块一键与选定对象操作。
- **M6 台账 CRUD**：四类台账可亲笔增删改、去截断、全部走日志可撤销。
- **M7 世界线与预言书**：`worldline/` 带类型读写层 + 纯函数布局；
  三种看法（并轨 / 世界树 / 对比）；从任意节点分叉；节点手改；三栏卷轴；
  **时间轴铺满整页**（轨道列表与详情都是浮层）：横轴=章节，α 主干横贯中线，
  每条 if 从分叉章用 S 曲线弯出去再平走——"现在是一条线，前面是无数种可能"。

  **它自己的分叉章高度**水平伸出去、再竖直向上长；线宽按血缘深度递减；
  **一条世界线一个颜色**（正典固定蓝，其余走调色板）——"不同的世界发展线路"
  靠颜色分最省地方；实/虚按线的性质分：正典与已扶正=实线，预测/假设=虚线；
  根下有「现在」标记；画布按窗口尺寸算坐标、铺满整页；没写 parentId 的线
  挂到正典下；父线被删的线也挂正典（避免树碎成几根互不相连的柱子）；
  **逐节点采纳**（`Store::adopt_node`：节点转 `adopted` 状态 + 产出
  `plannedEvent` 提案过收件箱；时间轴上蓝实心 = 已采纳待写）；
  **缩放平移**（`layout::zoom_window` / `pan_window` / `focus_window`，纯算术带测试：
  以中心为轴、跨度不低于 8 章、越界靠平移而非裁剪）；
  **节点抽屉**（点轴上的点浮出：备注、双向因果链、章号+1、采纳、推演、删除）。

  界面上的铁律就只是界面文案，模型看不到。作者可自行修改。
- **M8 技能库与创造模式**：16 个技能替代硬编码任务书；官方 `tool-cordis`

### 一个踩了很久的坑：`cubic_bezier_to` 的参数顺序

gpui 的 `cubic_bezier_to(to, control_a, control_b)` —— **终点是第一个参数**，
和几乎所有图形库（canvas / SVG / CoreGraphics）的 `(c1, c2, to)` 相反。
整仓 68 处调用一直按常见顺序写，结果所有曲线和"圆"都画歪：
圆点变成三角尖刺、分叉曲线变成漫过整屏的斜线。视觉上像是布局算法错了，
实际是绘图 API 的参数顺序错了。修法：全量交换参数，并在 `worldline/view.rs`
里留了一条说明。

## 10. 无限画板 · 世界线 · 预言书（多重世界线）

> 命名沿革：本节「世界线」排期板原名「导演台」（对齐 AI 短剧工具的叫法），2026-11-10 更名。

对标 AI 短剧工具的「无限画板 + 导演台」，但执笔的对象不是分镜，而是**叙事结构本身**：
剧情线路、人物关系、暗线发展、因果影响与延伸——再加上一个别家没有的东西：
**预言书**——多重世界线的假设推演，以及每条世界线对原始设定的影响清单。

### 10.1 四页分工（先说清概念，否则界面一定做歪）

这四个词以前混用过，先钉死定义：

| 概念 | 定义 | 回答什么问题 |
|---|---|---|
| **世界线** | **剧情的发展方向与时间节点**。前面的剧情固化后，后面可能产生的所有 if 线。横轴就是章节。 | 「故事确定到哪儿了，之后有哪些可能？」 |
| **画布** | **关系网**。剧情关节节点、设定、道具、人物之间的关联关系：张三 → 他的人物关系 → 他的事件与剧情发展。 | 「这个关节跟谁有关、牵扯到什么？」 |
| **预言书** | **if 工坊**。在某个固化点上分叉出来的假设线，以及每条线对正典的影响清单。 | 「这条假设如果成真，正典会变成什么样？要不要收？」 |
| **排期板** | 章 × 幕的工作排期。**与世界线无关**，读的是 events/clues/stages。 | 「下一章该写什么，伏笔到期没？」 |

**世界线与画布的关系**：两者正交，靠**双向弱引用**连起来。
- 世界线节点 = 时间轴上的一个关节（「第 12 章发生了观灯人现身」）
- 画布节点 = 关系网上的一个点（「观灯人跟沈砚是什么关系」）
- 世界线节点的 `canvasRef` 指回画布节点；画布侧反查得到「它在哪几条线的哪一章」。
- **弱**的意思是：画布节点被删了，世界线不会崩，只是查不到关系。

**固化**有两层含义，两者都要支持：
1. **边界**：α 正典的固化边界 = 最新成稿章（写出来的都定了），之后是开放的 if 空间。
2. **扶正**：作者从某条 if 线里选定一条，它成为正典的后续（`Kind::Fixed`），
   全局固化边界推到它的末尾。原正典保留（用于对比「扶正前是什么样」）。

### 10.2 四个页面的分工

| 页面 | 是什么 | 核心动作 |
|---|---|---|
| **世界线 Worldline** | **时间轴**。横轴 = 真实章节；固化段实线、开放段虚线；每条 if 从它的分叉章长出。页内三个看法：**时间轴** / **世界树**（纵轴章节、横轴子树宽度、可钻取）/ **对比** | 选章节、从任意处再分叉、改节点章号、连/删因果边、标暗线、折叠轨道、扶正、归档、删除 |
| **画布 Canvas** | **关系网**。七维（总览/设定/人物/关系/时间/事件/转折），节点是人物/设定/道具/事件，边是人物关系与剧情关联 | 框选、拖节点、看一阶影响半径、读者视角；选中节点看它**在世界线上的落点** |
| **预言书 Oracle** | **if 工坊**。选中一条线 → 看推演卷轴（按章分段的因果链）→ 看影响面 → 逐条或批量晋升 | 写假设 → 让 AI 推演 → 看影响清单 → 晋升为提案 |

### 10.2b 专属 Agent 是能力，不是对话对象

六个专属 Agent（人物/关系/世界线/预言/大纲伏笔/校审）**没有聊天窗口**。
它们是被调用的执行者，三条入口：

| 入口 | 谁决定路由 | 例子 |
|---|---|---|
| **模块一键能力** | 页面写死 | 人物页「全量补全」、大纲页「伏笔盘点」 |
| **指定对象操作** | 页面写死 + 带上对象描述 | 选中沈砚 →「补全这张卡」；选中某个节点 →「从这儿往后推」 |
| **主 Agent 推断** | 主 Agent 按路由表自己判断 | 作者说「把第 12 章的人物关系捋一下」→ 派给 `relations` |

前两条为什么页面要写死：作者点按钮时意图已经明确。这时再让主 Agent 挑，
它可能挑错、可能自己干了、也可能反过来问作者——三次都算失败。

第三条靠 `capabilities::routing_hint()` 注入主 Agent 的系统提示：
**"什么任务 → 派给谁"** 的显式映射表，而不是让模型从 Agent 名字猜。

技术约束：DSH sdk 协议没有"直接给某个 preset 发消息"的方法，子 agent
只能由主 agent 通过 `tool-subagent` 派。所以三条路最终都经过主 Agent，
区别只在路由由谁决定。
| **排期板 Director** | 章 × 幕排期板（原名「导演台」）。事件卡/伏笔卡拖进章节 | 拖卡改期 → 触发骨架合同核对 |

> 曾经的错误：三视图（并轨/世界树/对比）全塞在「预言书」页里，
> 而「世界线」这个词在侧栏出现两次——一次指排期板、一次藏在预言书里，
> 而真正的世界线（时间轴 + 固化点 + if 分支）**没有自己的页面**。
> 画布的「预言维」更是把世界线当成关系图渲染，方向就是反的。
> 2026-11 已按上表重排。

### 10.3 数据模型（worldlines.json，沙盒与正典物理隔离）

```
worldlines.json: [{
  id, name, premise(假设一句话), kind: base|fixed|forecast|what-if,
  parentId, forkNode(从父线哪个节点长出), forkedChapter,
  fixedThrough(这条线自己固化到第几章), tookOver(被扶正时留痕),
  status: 推演中|已定稿|已归档,
  nodes: [{id, kind, label, reference(正典id), canvasRef(画布节点id，双向弱引用),
           chapter(真实章节落点), note, state: planned|written|branch-only, x, y}],
  edges: [{from, to, kind: plant|payoff|involve|conflict|influence|hiddenline}],
  diffs: [{target, targetRef, kind: add|change|remove, before, after, reason, severity}],
  derived: {characters: [...], canon: [...], clues: [...]}   // 本线专属衍生，不碰正典
}]
画板坐标/连线布局存 canvas.json（viewState：缩放、平移、节点位置、分组折叠）。
正典数据（storylines/events/clues/canon/memory）仍是唯一事实源；世界线只引用 ref 或标 new。
```

### 10.4 铁律映射（一条都不能松）

- 推演 = 提案：预言书的推演结果只写 worldlines.json（沙盒），**永不直接改正典**；
- 影响清单每条 diff 有「晋升」按钮 → 生成对应 propose_* 提案（canon/clues/outlineUpdates）→ 进收件箱 → 作者采纳才落正典；
- 衍生人物/设定默认 `line:<worldline-id>` 归属标记，切线可见、跨线不可见；晋升后转正式；
- 暗线（hiddenline 边）在画板默认虚线+低透明，「读者视角」模式一键隐藏——信息差可视化。

### 10.5 novel-pack 工具面

| 工具 | 语义 |
|---|---|
| `get_world_state` | 读正典图数据（线/事件/人物/伏笔/设定 + 关系边）供画板与推演 |

## 11. 世界线双态 × 多维织网画布（M8，2026-11-10 用户定案）

用户口径：**世界线 = 已固化线 + 预测线**；**画布 = 把设定/剧情/关系/事件/转折按维度织成明确的网**。

### 11.1 世界线双态（worldlines.json 增 `kind`）

| kind | 语义 | 数据来源 | 写权限 |
|---|---|---|---|
| `base`（α） | 正典基准 | 全部台账 | 只读 |
| `fixed` | **已固化**：已写完确定下来的剧情 | 自动派生：`happened=true` 事件 + 已成稿章节（只读视图，不落文件） | 只读展示 |
| `forecast` | **预测线**：按大纲/设定（无大纲则按已成稿）推演后续剧情 | AI `forecast_task` → simulate 工具写沙盒；diffs=计划剧情，晋升走 outline/clues/skeleton 提案 | 沙盒 only |
| `what-if` | 假设推演（原预言书能力） | 同上 | 沙盒 only |

固化线给用户「织到哪了」的全景；预测线给用户「接下来往哪织」的可选路——都是整理辅助，铁律不变：预测晋升成提案、采纳才进正典。

### 11.2 多维画布（CanvasPanel 顶栏维度页签）

每维 = 节点类型子集 + 专属布局 + 专属边映射（全部真实数据，零臆造）：

| 画布 | 节点 | 边 | 布局 |
|---|---|---|---|
| 总览 | 五类全量 | influence/plant/payoff/involve | 列式（现行） |
| 设定 | canon（分类着色，meta=类别） | facts.object↔canon 命中边 | 网式（两排均布） |
| 人物 | characters（canonical+aka） | involve（facts.subject×fromChapter→事件） | 列式 |
| **关系** | characters | **subject→object 且两端可经别名表归一** → 人名↔人名边，label=predicate（获得/师徒/敌对…） | 中心辐射（主角居中） |
| **时间** | events 按章 | chapter 顺序链边 + 挂线 storylines | 横轴时间线（每行 8 事件折行） |

### 12.2 本轮落地的结构件

| 结构件 | 位置 | 它保证了什么 |
|---|---|---|
| 依据区 | `app/src/inbox.rs::payload_basis` / `basis_block` | 每条提案先回答「凭什么」：`sourceRefs` 显式引用优先，其次从既有字段推导；自述（`note`）单列，不算依据；无依据显式警示。 |
| 内容预览 | `payload_preview` / `preview_block` | 把 payload 里真正会写入的东西逐条列出（beats/findings/original→replacement/草稿正文/报告证据…），默认折叠、可展开；不再只给数量。 |
| 落点 · 回滚 | `payload_effect` / `effect_block` | 每张卡写明采纳会改哪里、原文件备份到哪（正文快照 / `canon/backups/` / `snapshots/ledger/`）；多条目提案额外写「粒度：整单处理 N 条」，撤销粒度与动作一一对应。 |
| 决策账本 | `ledger_footer` | 待拍板/已决/采纳率常驻面板底部，不随滚动跑掉。 |
| 已决历史 | `history_row` | 已处理提案保留状态、时间、拒收理由、payload 预览与持久化的 `applyResult`（实际入库/跳过条数）；默认最近 12 条，可「显示全部」回看，不再只剩一个计数。 |

### 12.3 与竞品的结构差异

同样是「AI 辅助写作」，差别不在文风，而在**决定发生在哪一步、决定留下了什么**：Sudowrite 把设定静默拼进提示词、300 词续写直接落进正文，作者只剩「插入/忽略」——我们把引用条目摆进依据区、正文写入必须点击采纳且卡片先写落点与回滚；NovelAI 一口气往下流、分支历史藏在文件里、导出即抹平——我们的提案落盘、已决历史与正文快照都在界面里可回看；彩云小梦让作者在模型写好的三条里挑一条、决定空间由模型划定——我们的决定对象是提案条目（条目级采纳仍是缺口，见 12.4），且提案永不直接进正文；笔灵用模板关键词一键成文再「降 AIGC 痕迹」——我们不做抹除来源的后处理；MidReal 一次点击生成一本书、harnessNovel 自动补字数跑完整条流水线——我们一次点击只处理一条提案，没有自动执行通道。

### 12.4 已知缺口（诚实清单）

1. **条目级采纳未拆**：`apply_payload` 以提案为单位；`app/src/workspace.rs` 的导入提示、novel-pack `propose_deslop` 描述与 §4.3 旧文「批量操作保留」仍与实现不符（导入提示与 §4.3 未动）。
2. **依据不可点回**：依据区列出编号/标题，但没有跳到设定页、伏笔台账或正文位置的导航。
3. **生成前决定点枚举未做**：决定点只在生成后以提案条目呈现。
4. **输入快照不完整**：没有记录引用条目的版本、生成参数与模型；决策树/分叉对比未做。
5. ~~**正文来源标记未做**~~ **已补（M3）**：AI 改过的正文区间写进
   `chapters/ch-NNN/ai-marks.json`，编辑器左缘显示墨点；改动撤销后标记同步清除。
   仍然没有的：逐段"这段是 AI 写的还是我写的"的完整溯源，墨点只记"有 AI 参与"的区间。
6. **落库后的只读查看**：`meta.beats` / `meta.report` 采纳后没有独立只读页；已决历史可展开回看 payload 与持久化的 `applyResult`（入库/跳过条数），但看不到落库后文件的当前内容。
7. **`sourceRefs` 覆盖面有限**：`propose_canon`/`propose_clues` 与预言书晋升（canon/canonRevise/clues/outlineUpdates/plannedEvent）会产出该字段；其余 kind 靠既有字段推导（report/deslop/clueFixes/outlineUpdates/memoryPack/dossier/canon/canonRevise/plannedEvent），推导不出的显式标「未提供依据」。
8. **引用来源未做成硬闸门**：`app/src/prompts.rs::BASIS_RULE` 只是提示词要求，工具 schema 里的 `sourceRefs` 仍是可选字段；当前靠界面把「未提供依据」显性化，生成端不拦截。
9. ~~**非正文台账快照无恢复入口**~~ **已补（M3/M6）**：改动日志为每次落库存前像
   （内容寻址），「改动记录」页可按条或按批撤销，带冲突检测。`snapshots/ledger/`
   仍保留，但不再是唯一恢复途径。
10. **部分成功仍显示「已采纳」**：多条目提案部分跳过时状态仍为「已采纳」，已决历史用 `applyResult` 显示实际入库/跳过条数，但没有独立的「部分采纳」状态。

11. **世界线树布局是槽位均分**：`worldline/layout.rs` 做的是 tidy-tree 的简化版
    （叶 1 槽、父 = 子树之和）。它保证可复现、不重叠，但没有做力导向或
    最小交叉优化——节点特别多时枝会靠得较近。

12. **对比模式只比"共同祖先之后"**：`layout::compare` 用章节切分而非严格
    按节点集合差异。如果两条线在共同祖先之前就各自改过节点，这部分差异
    不会被报出来。

13. **逐节点采纳仍是两步**：`adopt_node` 产出 `plannedEvent` 提案，作者还要在
    收件箱再点一次才进 `events.json`。有意为之（AI 推出来的节点不该绕过裁决），
    但界面上它看起来像"采纳了"，容易误解。

14. **插件开关的粒度是 patch 行**：一个 npm 包可能对应多行（`tool-cordis` +
    `cordis-host-runner` + provider 注册），插件页只暴露能安全关掉的那些，
    没有"整个包开关"的入口。关掉后要重启运行时才生效。

15. **本书专属 Agent 的接管是"提示词级"**：`takeover` 只改主 Agent 的
    personaPrefix 一段话，不是硬约束。主 Agent 仍可能自己把活干了——
    要硬约束得改 `tool-subagent` 的派活策略，那属于对 DSH 的魔改，没做。
